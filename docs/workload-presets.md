# Workload presets: where the figures come from

The presets in `src/lib/presets.ts` fill the typical-load fields on the VRAM calculator and the Capacity Plan page. Lengths are means of production traces where any are public, and of benchmark datasets where none is. Latency targets are MLPerf Inference's p99 limits, which are benchmark gates rather than product SLOs. Collected on 2026-10-13. Figures marked "computed" were recomputed from the released trace files, not taken from a summary.

|---|---:|---:|---:|---:|---:|---|
| chat | 1,000 | 250 | 500 | 0.5 s | 40 ms | medium overall |
| rag | 4,000 | 200 | 200 | 2 s | 40 ms | low-medium |
| code | 2,000 | 25 | 0 | 0.3 s | 30 ms | medium-high for lengths (two large Azure production traces agree; likely completion-style, the workload is not named beyond 'coding'); medium for latency; sharedPrefix medium (no trace measures it, but FIM prompt formats carry no system prompt) |
| agent | 10,000 | 200 | 4,000 | 2 s | 20 ms | medium for lengths and sharedPrefix (one production generic-agent trace, plus coding-agent traces an order of magnitude larger); low-medium for latency (no published agent SLO; values are benchmark limits and observed speeds) |
| summarization | 8,000 | 250 | 50 | 6 s | 100 ms | medium |
| reasoning | 1,000 | 4,000 | 100 | 2 s | 40 ms | medium |

Thinking models add 1,000 tokens to a non-reasoning reply: Alibaba's production DeepSeek-R1 traffic (ServeGen) averages 1,527 output tokens, about 70% of them reasoning.

**Caveat on prefix reuse.** The shared prefix is the part every request repeats. Within a session much more is reused: total prefix-cache hits run about 40% for chat, 59% for agents and 96% for coding agents in the traces below. The planner discounts only the shared prefix, so for multi-turn chat and agents it overestimates prefill work.

## chat

Production conversation traces put the mean full prompt (history included) between about 700 and 1,650 tokens (Azure 2023/2024, BurstGPT, Alibaba ServeGen) and mean replies between 106 and 343 (most of them 200 to 300), so 1,000 in and 250 out. The shared prefix is the one global system-prompt block that Kimi's production trace shows (512 to 1,023 tokens), rounded down because many chat templates are far shorter. The latency is MLPerf's Interactive chat limit (Llama 2 70B: 450 ms TTFT, 40 ms TPOT at p99), which MLCommons derived from ChatGPT and Perplexity streaming rates, with TTFT rounded to 0.5 s.

Confidence: medium overall: lengths high (many independent production traces agree), sharedPrefix low-medium (one production trace with 512-token granularity), latency medium (MLPerf p99 limits, not product SLOs)

## rag

No public production RAG trace exists. 4,000 tokens is the 'typical RAG context' that CacheBlend (citing RAGCache) uses and roughly a few 512-1,024-token chunks plus a question. It sits between short-passage setups (RAGO's 512, MLPerf E2E-RAG's ~770) and the long-context QA benchmarks (LongBench multi-document QA, 4.9k-11.2k words). The answer is short: 200 sits between factoid QA caps (32-128) and the long-form or pipeline measurements (~220-256). The shared prefix is only the instruction template, because retrieved chunks change with each query. TPOT matches chat because a person reads the streamed answer. TTFT is MLPerf's standard 2 s server TTFT, which leaves room for a longer prefill than chat (MLPerf's 9.4k-token long-context benchmark allows 4.5-6 s).

Confidence: low-medium: lengths rest on benchmark and pipeline design choices, not a production trace; sharedPrefix low; latency is chat-derived (MLPerf has no latency limit for its offline-only E2E-RAG benchmark)

## code

Azure's production code-completion traces have mean prompts of 2,048 (2023) and 2,511 (2024) tokens and mean outputs of 28 and 23 (medians 13 and 8), so 2,000 in and 25 out; 25 is also Meta CodeCompose's single-line cap. Fill-in-the-middle completion prompts are file-specific with no shared system prompt, so the shared prefix is 0; reuse happens only within a session. TTFT follows shipped products, which target sub-300 ms suggestions (CodeCompose median single-line 280 ms end to end; Google <100 ms budget). It sits between DistServe's 0.125 s and MLPerf's 0.5 s code-assistant Interactive limit. TPOT is MLPerf's 30 ms Interactive limit, which MLCommons motivates with code assistants.

Confidence: medium-high for lengths (two large Azure production traces agree; likely completion-style, the workload is not named beyond 'coding'); medium for latency; sharedPrefix medium (no trace measures it, but FIM prompt formats carry no system prompt)

## agent

Kimi's production tool and agent trace averages 8.6k input and 182 output tokens (median output 30). Agent traffic in 2025-26 runs longer (OpenRouter coding >20K; Claude Code/Codex steps ~120-140k), so the prompt is rounded up to 10k for a generic tool-calling agent; coding agents need a custom ~120k. The shared prefix uses the same trace: requests on agent-specific templates share 2.6-6.7k tokens, and all requests together average ≈3.0-3.3k. 4,000 also covers the 2-26k that single MCP servers' tool definitions take. Agent steps run back to back, so decode speed sets loop time. 20 ms matches observed production agent decode (~47 tok/s) and MLPerf's GPT-OSS-120B Interactive limit. TTFT 2 s is MLPerf's Interactive GPT-OSS limit; observed Codex steps take ~3 s.

Confidence: medium for lengths and sharedPrefix (one production generic-agent trace, plus coding-agent traces an order of magnitude larger); low-medium for latency (no published agent SLO; values are benchmark limits and observed speeds)

## summarization

Long-document summarization benchmarks cluster at 7-9k input tokens and 200-230 output (arXiv summarization in Sarathi-Serve and Mooncake), and MLPerf's long-context set is 9.4k in and 680 out. News summarization is far shorter (CNN/DailyMail 778 in, 73 out), so 8,000 in and 250 out. The shared prefix is only the instruction template: about 30 tokens in MLPerf's CNN/DM prompt, and Mooncake measures ~0% prefix reuse on arXiv summarization. Latency matters less here (Splitwise and DistServe treat summarization as loose-TTFT): TTFT comes from MLPerf's 6 s long-context server limit, and TPOT is MLPerf's 100 ms summarization server limit, between GPT-OSS PubMed's 80 ms and DistServe's 150 ms.

Confidence: medium: lengths come from benchmarks, not production (no public summarization trace); latency from MLPerf server limits; sharedPrefix medium (measured ~0%)

## reasoning

MLPerf's DeepSeek-R1 workload (math, QA and code prompts) averages 800 input and 3,880 output tokens. Alibaba's production DeepSeek-R1 traffic averages 1,268 in and 1,527 out (about 70% of it reasoning). Hard math goes much further: 9-23k tokens on AIME. So 1,000 in and 4,000 out, matching the industry benchmark; production traffic is lighter. The shared prefix is small because DeepSeek advises no system prompt; gpt-oss needs only a short Harmony system message. TTFT is MLPerf's DeepSeek-R1 server limit of 2 s. TPOT 40 ms sits between R1 Server (80 ms) and Interactive (15 ms, which needs MTP speculative decoding). It matches the 25 tok/s p99 floor MLCommons uses for interactive chat, since many UIs stream the reasoning.

Confidence: medium: output length is highly task-dependent (1.0k-23k across sources), and benchmark and production disagree about 2.5x; latency medium (MLPerf p99 limits); sharedPrefix low-medium

## Notes

Method. Where a dataset or trace is public, I recomputed the statistics myself from the released files (October 2026 downloads): Azure LLM inference traces 2023 and 2024, BurstGPT_1.csv, the Mooncake FAST'25 traces with hash_ids, and the ServeGen distributions. All other figures are quoted from the cited paper, page or repo. Every 'computed by me' figure is marked in its 'what' field. Means are used for presets because capacity scales with mean tokens; medians are far lower for skewed traffic (Azure 2024 conversation: mean output 106, median 41).  Tokenizers. LMSYS-Chat-1M and Anyscale used the Llama 2 tokenizer. MLPerf feeds token IDs from each benchmark's reference model tokenizer (Llama 2/3.1, DeepSeek, gpt-oss o200k_harmony), but the length figures themselves do not name it. The Azure, BurstGPT, Mooncake (Kimi), ServeGen (Qwen/DeepSeek) and TraceLab counts come from the production model's own tokenizer and are not stated. LongBench reports words, not tokens (roughly 1.3 tokens per English word). Counts across sources can differ by about ±20% for the same text.  Prompt vs shared prefix. promptTokens in production traces includes multi-turn history and tool results. sharedPrefix is meant as the global system prompt or tool schema only. Session-local reuse (history) is much larger in practice: total prefix-cache hit is ~37-40% for Kimi conversation, 57-59% for Kimi tool&agent, 74% for Chatbot Arena and 95.7% for coding agents, against a global-prefix share of ~5-35%. A planner that only discounts sharedPrefix will over-estimate prefill compute for chat and agents.  Mooncake figures. The arXiv-report trace and the FAST'25 Tool&Agent trace are the same 23,608 requests. Earlier arXiv versions gave the average input as 7,590; v5 and the FAST'25 table give 8,590 and 8,596, which match my computation (8,590 for the arXiv file, 8,596 for the FAST'25 file).  MLPerf. Limits come from the master branch of mlcommons/inference_policies (inference_rules.adoc) as of 2026-10-13, which covers v6.1 and in-progress changes. The scenario table gives a 99% tail for Server/Interactive, and the MLCommons blogs call the TTFT/TPOT limits 99th-percentile. TPOT is the mean inter-token interval per request. The Llama2-70B and Llama3.1-8B 'Server' scenarios are now labelled 'Conversational' in the rules. The GPT-OSS-120B Interactive TPOT is 20 ms in the rules but 15 ms in the v6.0 announcement blog; I treat the rules as normative. MLPerf limits are p99 benchmark gates, not product SLOs. A planner that sizes to mean or median latency can use somewhat looser numbers.  Fixed-shape benchmark conventions, for context. NVIDIA NIM/AIPerf use-case pairs: translation 200/200, classification 200/5, summary 1000/200, code generation 200/1000. InferenceX defines an 8K/1K prefill-heavy shape and replays real agent sessions (AgentX) for agentic work. I could not confirm from a SemiAnalysis primary page the 1K/1K and 1K/8K pairs that third-party write-ups attribute to it. Anyscale LLMPerf uses 550/150.  Thin evidence. (1) RAG: there is no public production RAG trace, so the RAG lengths rest on benchmark and pipeline design choices (512 to ~4k context). (2) The ShareGPT mean as sampled by today's vLLM benchmark_serving with a Llama-3 tokenizer is not published anywhere I could find. The vLLM paper's 161 in / 338 out is the closest primary figure; I could not recompute it without a tokenizer. (3) Agent latency has no published SLO; the values are MLPerf limits and observed production speeds. (4) Chat sharedPrefix rests on one provider (Kimi) at 512-token granularity. (5) Reasoning output: the benchmark mean (MLPerf 3.9k) is 2.5x the production mean (Alibaba R1 1.5k), so it depends heavily on task difficulty. (6) The code preset reflects inline completion; chat-style or agentic coding is far longer (20k to 140k input) and belongs under agent with a custom prompt size.
