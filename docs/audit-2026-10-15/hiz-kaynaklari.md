## Caveats per point

- **N\* (NIM):** The NIM doc does not state the H100 form factor. A 1x H100 80G NIM setup is almost certainly SXM, but the page does not say so. The engine is the NIM's TRT-LLM backend (NIM LLM 1.x), not vLLM. ITL at c=1 is the TPOT to compare against a roofline. The tok/s column is client output throughput, which at c=1 already includes TTFT. Within the 8B fp8 20k config, NIM 1.3.0 gives ITL 11.3 ms but 1.8.0 gives 5.06 ms, so the version matters a lot for long-context decode.
- **N4:** H200 BF16 ITL (7.11 ms) is slower than H100 BF16 (6.52 ms), even though H200 has more bandwidth (4.8 vs 3.35 TB/s). The likely cause is a config or profile difference. Don't use this point as a bandwidth anchor.
- **N6 roofline check (my arithmetic, not from the source):** For 8B at 20k tokens, linear FLOPs ≈ 2 × 6.98e9 × 20k ≈ 2.8e14 and causal attention ≈ 1.05e14, about 3.8e14 in total. FP16 at 637.84 ms is about 60% of the H100 SXM dense BF16 peak (989 TF). At 5k tokens, 128.32 ms is likewise about 60%. Both are plausible.
- **A1–A3:** The figure is end-to-end latency for prefill plus 2048 decode steps. ms/tok is derived as latency / 2048, which slightly overstates TPOT because it includes prefill. The H100 number was run by AMD on TRT-LLM 0.16, a competitor's run.
- **T1:** The page shows no speculative decoding in the low-latency YAML (attention DP off, TRTLLM MoE backend, CUDA graphs). It runs TP8 on 8 B200 to minimise latency. It does not state the KV cache dtype.
- **L1–L3 (LMSYS DGX Spark):** The software was early-stage (the authors say so). The prompt and output lengths are not stated. Their own figure for 8B FP8 is 20.5 tok/s, against a weights-only upper bound of about 34 tok/s (8 GB at 273 GB/s), so about 60%. The precision of the 70B row is ambiguous between FP8 and q4_K_M. The gpt-oss rows are Ollama, not SGLang.
- **G\*/S\*/H\*/C1 (llama.cpp):** tg numbers are generation at the given context depth (d0 = empty), single stream, with no speculative decoding. Model sizes are the GGUF file sizes in GiB that llama-bench reports. The MoE models (gpt-oss, Qwen3-30B-A3B) read only the active experts per token: gpt-oss-120b has about 5.1B active params, gpt-oss-20b about 3.6B, and Qwen3-30B-A3B about 3.3B. The scoreboard lists "H100 80 GB" and "A100 80 GB" without SXM or PCIe, and lists L40 (not L40S). The tg128 runs in C1 used different commits.
- **C1 roofline note (my arithmetic):** The 7B Q4_0 model is about 3.82 GB. The RTX 4090 reaches about 72% of its 1008 GB/s, and DGX Spark about 79% of its 273 GB/s. The H100 reaches only about 32% of 3.35 TB/s (281 t/s vs about 877 t/s at full bandwidth). On fast HBM cards, a small model at batch 1 is limited by kernel launch and synchronisation overhead, not by bandwidth. A pure bandwidth roofline therefore over-predicts small-model batch-1 speed on H100, A100, and B200.
- **X1/X2 (XiongjieDai):** These use a May 2024 llama.cpp build. The README names the prompt sizes (-p) but does not say which one applies to the tg columns, so treat tg as near-empty context. F16 on the A100 SXM (53.5 t/s) is only about 42% of its 2.04 TB/s, so this old build's F16 CUDA path is not bandwidth-efficient on HBM. Use these points for consumer cards, but not to calibrate HBM cards.
- **H1–H3 (Wendell, Level1Techs):** The post gives no llama.cpp build number. The "Strix Halo" machine is unnamed in the parts I fetched. It runs the ROCm backend through a kyuz0 toolbox. These points match the user's GTR9 (Ryzen AI Max+ 395) hardware class. An earlier (Aug 2025, build 6118) run of the F16-labelled 60.87 GiB gpt-oss-120b GGUF on Vulkan gave tg128 33.06/33.16 (https://community.frame.work/t/tracking-will-the-ai-max-395-128gb-be-able-to-run-gpt-oss-120b/73280). The jump to about 52 t/s shows how much the build and backend matter.
- **H4:** The author measured about 215 GB/s of usable GPU memory bandwidth, against 256 GB/s theoretical. Use 215 GB/s as the effective-bandwidth anchor for Strix Halo.
- **I1:** InferenceX values are interpolated onto per-user targets. Concurrency and TP are not shown. It is a sanity check only.
