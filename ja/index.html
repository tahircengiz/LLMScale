LLM VRAM 計算ツール：モデルの重み、KV キャッシュ、GPU 適合性

LLMScale は、大規模言語モデルに必要な GPU メモリ（重み、KV キャッシュ、コンテキスト ウィンドウ、同時ユーザー数）を各モデル自身のアーキテクチャから計算し、どの GPU に収まるかを示します。モデルを選び、ワークロードを調整してください。

精度とワークロード

オフのときは、全ユーザーがコンテキスト ウィンドウ全体を使います。これは vLLM が「Maximum concurrency」として報告する最悪のケースです。オンのときは、各リクエストが平均してプロンプトと応答の半分を保持し、すべてのプロンプトに共通するプレフィックスは 1 回だけキャッシュされます。

重み、KV キャッシュ、オーバーヘッドは、モデル自身の設定ファイルからブラウザ内で計算されます。上で Hugging Face を検索するか、プリセットから始めてください。

数値の計算方法 ▸▾

重み = パラメータ数 × バイト/パラメータ（FP16/BF16 = 2、FP8/INT8 = 1、INT4 = 0.5）。Mixture of Experts（MoE）モデルではすべてのエキスパートが読み込まれるため、アクティブな一部ではなく総パラメータ数を使います。

KV キャッシュ = 2 × 層数 × kv_heads × head_dim × バイト数 × コンテキスト × 同時リクエスト数。グループ クエリ アテンション（kv_heads < attn_heads）はこれを大幅に小さくします。この値は各モデルの設定ファイルから読み取ります。Multi-head Latent Attention（DeepSeek）では、代わりにトークンあたり「層数 × (kv_lora_rank + qk_rope_head_dim) × バイト数」をキャッシュします。vLLM が確保するとおりに計算します。sliding window の層はウィンドウに加えて処理中のすべてのトークン（--max-num-batched-tokens の 2 バッチ分）を保持し、Mamba や線形アテンションの層は状態ブロックを 2 つ保持します。

オーバーヘッド は、vLLM 0.31 が重みとキャッシュ以外に各 GPU で確保するメモリです。ランタイム バッファ（バッチ化しうるシーケンスごとに、語彙 1 エントリあたり 4 バイト）、プロファイリング実行のピーク（バッチ化されたトークンに対するフィードフォワード ブロックと出力層のうち大きいほう）、CUDA グラフで構成されます。テンソル並列では、各 GPU がそれぞれを持ちます。vLLM の起動 11 回分と照合したところ、vLLM 自身の数値との差は 0.13 GiB 以内でした。各 GPU の予算は vLLM の --gpu-memory-utilization（デフォルトは 0.92）に基づきます。

見積もりは計画のためのもので、保証ではありません。実際の使用量は推論エンジン（vLLM、TGI、llama.cpp）とその paged attention の効率によって異なります。

この計算ツールの前提

LLMScale は各モデルのアーキテクチャ（層、アテンション ヘッドと KV ヘッド、ヘッドのサイズ）を Hugging Face Hub 上の config.json から読み取り、パラメータ数だけでなく、そこから GPU メモリを見積もります。Llama、Gemma、Mistral のようなゲート付きモデルは、ブラウザから config.json を読めないため、同梱のデータベースから取得します。GGUF のフォークのように独自の config.json を持たないリポジトリは、base_model から解決します。

どのカードも vLLM のデフォルトの割合であるメモリの 92% を予算とし、残りは CUDA コンテキストが使います。重みと KV キャッシュに加えて、各 GPU には vLLM 自身のオーバーヘッド（ランタイム バッファ、プロファイリング実行のピーク、CUDA グラフ）がかかります。これは実際の vLLM の起動と照合して計測した値です。統合メモリのデバイスでは、プール全体ではなく現実的な割合を使います。Apple の Mac ではメモリの 75%（36 GB 未満の機種では 3 分の 2）、Strix Halo と DGX Spark では GPU が報告するメモリに対する vLLM の 92% です。つまり、Strix Halo が GPU に割り当てる 96 GB のうち 88 GB、DGX Spark の 121.6 GB のうち 112 GB です（DGX Spark では vLLM を 80% で動かすことも一般的です）。各カードの予算は、ランタイムが報告するメモリ（公称サイズより少し小さい値）から始まり、ECC を有効にした GDDR のデータセンター向けカード（L40S、L4、T4）ではさらに 16 分の 1 少なくなります。デコード速度は、メモリ帯域幅（ベンダー公称ピークの 80%）とスパース性なしの Tensor コア演算性能のうち、遅いほうの制約で決まります。最初のトークンまでの時間は、キューイングなしの 1 リクエストについて、プロンプトの FLOPs から計算します。Tensor コア演算性能は、GeForce カードでは公称ピークの 90% としています。これは RTX 4070 Ti での vLLM の実測に基づきます（テストしたカードは、公称値の算出に使われたクロックより高いクロックで動作していました）。その他のカードでは推定として 60% を使います。これらの数値は容量計画のためのものです。実際の数値は、サービングエンジンとその PagedAttention の効率によってさらに変わります。

よくある質問

70B モデルにはどれだけの VRAM が必要ですか？
Llama 3.3 70B の場合、重みだけで BF16 では約 131 GiB、FP8 では 68 GiB、INT4 では 38 GiB です。706 億個のパラメータを 2 バイトで計算し、FP8 と INT4 では Transformer 層を 1 バイトまたは約 4.25 ビットとし、埋め込みと出力層は量子化チェックポイントと同様に 16 ビットのまま扱います。これに KV キャッシュとオーバーヘッドが加わり、どちらもコンテキスト ウィンドウとユーザー数によって変わります。それを算出するのがこの計算ツールです。
コンテキスト ウィンドウで答えが大きく変わるのはなぜですか？
KV キャッシュは、コンテキスト長と同時ユーザー数に比例して増えます。Llama 3.1 8B は FP16 で 1 トークンあたり 131,072 バイトを保持します。1 ユーザーで 8k トークンなら 1 GiB、128k なら 16 GiB です。さらに、8k でも 16 ユーザーなら同じく 16 GiB になります。
Mixture of Experts モデルは必要なメモリが少ないのですか？
メモリについては少なくなりません。すべてのエキスパートを読み込む必要があるため、メモリは総パラメータ数から見積もります。トークンごとに実行されるのは一部のエキスパートだけなので、MoE モデルはサイズから想像されるより速く生成します。
DeepSeek の KV キャッシュはどう扱われますか？
DeepSeek-V2 と V3 は multi-head latent attention（MLA）を使い、ヘッドごとのキーと値ではなく、層ごとに圧縮された潜在表現を 1 つキャッシュします。計算ツールは config.json から kv_lora_rank と qk_rope_head_dim を読み取り、層数 × (kv_lora_rank + qk_rope_head_dim) × バイト数をトークンあたりの値とします。DeepSeek-V3 の 8k コンテキストでは 0.54 GiB で、通常の式なら 13.34 GiB になるところです。DeepSeek-V3.2 のスパース アテンションと DeepSeek-V4 の圧縮アテンションも、同じようにそれぞれの config.json から見積もります。
