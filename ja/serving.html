サービングの概要：モデルのリポジトリからわかるサービング方法

モデルのリポジトリには、config.json 以外にも多くのファイルがあります。チャットテンプレートはツール呼び出しと思考を、generation_config.json はサンプリングのデフォルトと応答の終わりを決め、テンソル名からは実際に何が量子化されているか、マルチトークン予測の層が含まれているかがわかります。モデルを選ぶと、このページはブラウザ内でそれらのファイルを読み、デプロイでつまずきそうな点を指摘し、必要な vLLM と SGLang のフラグを書き出します。

リポジトリの読み取り方

このページは、エンジンがモデルを読み込む前に行うのと同じ方法でリポジトリを読み取ります。ファイル一覧とサイズは Hugging Face API から取得し、config.json、generation_config.json、tokenizer_config.json または chat_template.jinja、hf_quant_config.json、adapter_config.json、params.json はリポジトリにあれば読み取ります。テンソル名は model.safetensors.index.json から、単一ファイルのモデルでは safetensors ヘッダーから取得します。ヘッダーの読み取りはダウンロードではなく、小さな範囲指定リクエスト 2 回で済みます。処理はすべてブラウザ内で実行されます。

フラグを書くのは、vLLM 0.31.0 または SGLang 0.5.21 が、ドキュメントかパーサーの登録一覧でそのフラグを挙げている場合だけです。どちらも挙げていないモデル ファミリーには、推測でフラグを書くことはしません。MTP への対応状況は、各エンジンがドラフトモデルを構築するコードから判断しています。メモリ、並列構成、バッチ処理は、VRAM 計算ツールと vLLM パラメータのページに任せています。

よくある質問

MTP とは何ですか？なぜテンソルを確認するのですか？
マルチトークン予測層は、さらに先のトークンを予測するように学習された追加の層です。vLLM と SGLang は、これを投機的デコーディング用の組み込みドラフトモデルとして使えます。config.json に書かれているのは層がいくつあるべきかだけで、量子化版ではこの層が削除されていることがあります。DeepSeek-V3 の AWQ 版は MTP 層を 1 つ宣言していますが、元のモデルがこの層のために持つ 1,564 個のテンソルは 1 つも含まれていません。そのため、このページはテンソル名を確認します。
generation_config.json はなぜ重要なのですか？
vLLM と SGLang は、デフォルトの temperature、top_p、top_k と、応答を終了させるトークンをこのファイルから取得します。Qwen3 のこのファイルには終了トークンが 2 つ記載されていますが、config.json では 1 つです。gpt-oss のものは 2 つ追加しています。vLLM はさらに、ここにある max_new_tokens をサーバー全体の上限にします。
モデルにはどのツール呼び出しパーサーが必要ですか？
チャットテンプレートが出力する形式を読み取れるパーサーです。Qwen なら <tool_call> ブロック内の JSON、gpt-oss なら harmony のチャネル、Qwen3-Coder なら <function=…> 形式の XML です。このページはテンプレートとモデルタイプを読み取り、各エンジンのドキュメントがそのファミリーに指定しているパーサーを示します。名前はエンジンによって異なり、Qwen は vLLM では hermes、SGLang では qwen です。
リポジトリが宣言する量子化は信頼できますか？
通常は信頼できますが、根拠になるのはテンソル名です。ブロック単位のスケールを持つ FP8 は weight_scale_inv テンソルを、NVFP4 は weight_scale_2 を、MXFP4 は _blocks と _scales を、AWQ と GPTQ は qweight と qzeros を残します。NVIDIA の NVFP4 チェックポイントは、量子化を config.json ではなく hf_quant_config.json で宣言しています。このページは両方を読み取り、テンソル名と宣言が一致しない場合はその旨を示します。
