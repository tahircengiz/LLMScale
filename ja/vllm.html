vLLM パラメータ：用途に合わせて調整した vllm serve コマンド

調整済みの `vllm serve` コマンドを生成します。モデル、最適化の目標、ワークロードを選ぶと、LLMScale が性能、精度、信頼性を最大限に引き出すフラグを推奨し、コピーできるコマンドを示します。

最適化の目標

リストから選ぶ代わりに正確な数値を入力できます。このブラウザに保存されます。
vLLM のデフォルトに、このモデルと GPU に必要な設定を加えたもの。全ユーザー合計の 1 秒あたりのトークン数を最大化：大きなバッチ、GPU メモリをより多く使用、長いコンテキストには FP8 KV キャッシュ。各ユーザーへの応答を最速に：小さなバッチ、同時に処理するシーケンスを少なく。品質を犠牲にする設定は使わない：16 ビットの KV キャッシュと BF16 の重み。小さな GPU にできるだけ多く収める：メモリをより多く使用、FP8 KV キャッシュ、シーケンスを少なく。
3

ワークロード

対話型アシスタント。検索で取得した文章を含む長いプロンプト。コードの生成と補完。関数呼び出し：このモデル用のツール呼び出しパーサーを追加します。JSON スキーマに従う必要がある応答：構造化出力のバックエンドを追加します。プロンプト内の画像：リクエストあたりの画像数を制限します。思考モデル：リーズニングを回答から分離します。
ⓘvLLM を実行する GPU の数。このページは計算ツールと同じ方法で GPU を配置します。ヘッド数が許す範囲でテンソル並列、さらにパイプライン ステージ、レプリカ、MoE ではエキスパート並列を使います。
ⓘvLLM が受け付ける最長のリクエスト（プロンプトと応答の合計）。モデル上限 131,072

vLLM のログと照合

vllm serve が起動時に出力したログを貼り付けてください。LLMScale は vLLM 自身の数値を読み取り、上で設定したモデル、GPU、設定での見積もりと並べて表示します。ログはブラウザの外には送信されません。

vllm serve のフラグの選び方

モデル、GPU とその数、コンテキスト長、優先事項（バランス、スループット、低レイテンシ、最高精度、省メモリ）、タスク（チャット、RAG、コード、ツール使用、構造化 JSON、ビジョン、リーズニング）を選びます。このツールはそれを vllm serve コマンドに変換し、各フラグに 1 行の理由を添え、同じフラグを Kubernetes の args としても出力します。

  • --max-model-len = 設定したコンテキスト
  • --tensor-parallel-size、--pipeline-parallel-size、--data-parallel-size、--enable-expert-parallel = その数の GPU に対する計算ツールのレイアウト：vLLM がそれらの GPU でモデルを実行できる方式のうち、そのコンテキストでリクエストを保持できるものの中で最も高速なもの（その差が 10% 以内のものがあれば、その中で最も多く保持できるもの。スループットとメモリの優先時は、最も多く保持できるもの）。パイプラインのステージは、ほかのレイアウトでは保持できない場合にのみ使用（リンクやレイアウト選択で指定された場合はそのレイアウト）
  • --gpu-memory-utilization = スループットまたは省メモリを優先する場合は 0.95。それ以外は vLLM のデフォルト 0.92 のまま
  • --kv-cache-dtype fp8 = 省メモリまたはスループット優先で、コンテキストが 32k 以上か RAG タスクの場合。DeepSeek V4 では、vLLM のレシピに合わせて常に --block-size 256 とともに設定
  • --max-num-seqs = 512（スループット）、32（低レイテンシ）、64（省メモリ）。上限は、各 GPU が重みの分担分と vLLM のオーバーヘッドを確保した後に、KV キャッシュに収まる最大長のシーケンス数
  • vLLM 0.31 ではプレフィックス キャッシュとチャンク化プリフィルがデフォルトで有効なので、コマンドには含めません

ツール使用では --enable-auto-tool-choice とモデル ファミリーに合うツール呼び出しパーサーを、構造化 JSON では xgrammar バックエンドを追加し、ビジョンではプロンプトあたりの画像数を制限します。量子化済みのリポジトリ（AWQ、GPTQ、FP8、NVFP4）には --quantization フラグは不要で、ページにもそう表示されます。メモリ チェック（レイアウトの各 GPU で最大長の 1 リクエストを VRAM 計算ツール自身が見積もるもの）は、モデルが収まらない場合に警告し、計算ツールが求めたこの GPU の必要数と配置方法を示します。vLLM には Metal バックエンドがないため、Apple のデバイスは対象外です。

よくある質問

--gpu-memory-utilization は何をするのですか？
vLLM がモデルの重み、アクティベーション、KV キャッシュに使ってよい、各 GPU のメモリの割合です。重みが使わない分は KV キャッシュになるため、値を高くすると同時に処理できるシーケンスが増え、その GPU 上のほかの用途に残る空き容量は減ります。
--max-num-seqs が思ったより低いのはなぜですか？
このツールは、選んだコンテキスト長で KV キャッシュが実際に保持できる数を上限にしています。それより高く設定しても容量は増えず、上限を超えたリクエストはキューで待つだけです。
FP8 の KV キャッシュを使うべきですか？
KV キャッシュが半分になるので約 2 倍のシーケンスが収まりますが、長いコンテキストの処理では精度が下がることがあります。そのため、このツールはメモリかスループットが優先でコンテキストが長い場合にだけ提案し、まず検証するよう促します。
GPU は何基必要で、どう分割されますか？
重みとワークロードの KV キャッシュが収まるだけの数です。1 基で収まらない場合は、メモリ チェックが VRAM 計算ツールの算出した基数とレイアウトを示します。アテンション ヘッド数が割り切れる場合はテンソル並列、割り切れない場合やキャッシュをそれ以上分割できない場合はパイプラインのステージ、MoE ではエキスパートをデータ並列ランクに分散します。容量計画では、同じレイアウトを負荷に合わせて見積もります。
