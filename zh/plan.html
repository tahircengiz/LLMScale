这是一个针对平稳流量、平均长度且无突发的规划模型。读取提示会占用每个副本的一部分时间，并使解码按同一比例变慢；解码中的序列数遵循 Little's law。速度受以下因素约束：显存带宽按厂商峰值的 92% 计；稠密算力在 GeForce 显卡上按 90% 计（实测），在其他显卡上按 60% 计（估计）；此外每一步每层有固定开销，张量并行组内每层两次 all-reduce，每个请求在首个 token 之前约 6 ms。流水线的每个阶段各运行一个批次，速度与同等数量的副本相当；阶段间的交接和专家并行的分发按 all-reduce 计算开销，这是尚未实测的估计；在单个 NVIDIA GPU 上，结果与 vLLM 0.31 的实测值相差约 10–15% 以内。显存用量来自 vLLM 自身的统计。请为突发流量预留余量。在 Strix Halo 上，每层开销和算力均为实测值 (vLLM ROCm)，但超过四条序列以及短提示时最多慢 3 倍；在其他 AMD、Apple 和统一内存设备上，以及 MoE 的提示读取，速度仍是上限值。

规划是如何算出的

一个副本是一个 vLLM 实例，其布局与显存计算器的布局方式相同：单个 GPU、一个张量并行组、由这类组构成的流水线阶段，或者对于 MoE，是若干数据并行 rank，专家分布在它们上面。在给定的请求速率下，副本要把一部分时间用于读取提示。提示时间等于提示的 FLOPs 除以 GPU 可达到的稠密张量算力（GeForce 显卡为峰值的 90%，实测；其他 GPU 为 60%，估计），如果读取一遍权重所需的时间更长，则取后者。其余时间用于解码步，因此提示时间和解码时间会按同一系数拉长。给定批次大小下的单步时间来自解码模型：取读取权重和 KV 缓存所需时间与矩阵乘法所需时间中较长的一个。容量规划会找出能让首 token 延迟、每个输出 token 的时间和 KV 缓存都保持在限制内的最高速率，再用负载除以它。

  • 预填充占比 f = 每个副本的每秒请求数 × 预填充时间
  • 每个输出 token 的时间 = 该批次下的解码步时间 ÷ (1 − f)
  • 解码中的序列数 = 每秒请求数 × 输出 token 数 × 每个输出 token 的时间
  • GPU 数 = ⌈每秒请求数 ÷ 单个副本的容量⌉ × 每个副本的 GPU 数

它会尝试最多 8 个 GPU 上、能容纳一个最大上下文请求的所有此类布局；当模型需要更多 GPU 时，则尝试计算器给出的最少数量，并按成本从低到高列出。每个流水线阶段各自运行一个批次，所以由它们组成的副本与同样数量的单阶段副本一样快；正是流水线阶段让张量并行组放不下的模型得以容纳。共享前缀只缓存一次，不会重新计算。假定请求到达是平稳的，提示和输出长度用平均值表示，因此带有突发和长尾的真实流量需要额外的余量。

常见问题

为什么一个单 GPU 就能放下的模型会需要多个 GPU？
显存决定模型能否运行；负载决定需要多少个副本。每个请求先要读取提示，这一步受计算限制；之后它在每个解码步中占用一个位置，直到回复结束。Llama 3.1 8B 放在一块 H100 上还绰绰有余，但在 2,048 个 token 的提示、256 个 token 的回复、每 token 50 ms 的目标下，一块 H100 每秒约能承载 10 个请求，因此每秒 15 个请求就需要两块。
为什么张量并行有时不会多花 GPU？
把模型拆分到多个 GPU 上，会把每一步要读取的权重和每个提示所需的计算一并拆分，因此每一步更短，每个提示也能更快读完。当限制副本的是延迟目标时，两个 GPU 组成一个副本所能承载的负载可以超过单个 GPU 的两倍；当限制因素是 KV 缓存或原始吞吐量时，分开的多个副本同样好，而且更简单。
这些数字可信到什么程度？
它们是一阶估算。显存来自 vLLM 自己的统计方式，并已对照真实启动过程核对。速度采用厂商峰值和标明的效率，排队模型假定请求平稳到达。请把 GPU 数量视为平均负载下的下限，再为突发流量增加 20% 到 30%，然后在一个副本上用基准测试确认。
