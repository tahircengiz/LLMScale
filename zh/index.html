LLM VRAM 计算器 — 模型权重、KV 缓存与 GPU 适配

LLMScale 根据每个模型自身的架构，计算大语言模型需要多少 GPU 显存——权重、KV 缓存、上下文窗口和并发用户——以及哪些 GPU 能容纳它。选择一个模型，然后调整工作负载。

权重、KV 缓存和开销在你的浏览器中根据模型自身的配置计算——在上方搜索 Hugging Face，或从预设开始。

数值是如何计算的 ▸▾

权重 = 参数量 × 每参数字节数 (FP16/BF16 = 2, FP8/INT8 = 1, INT4 = 0.5)。对于混合专家模型，所有专家都会被加载，因此使用的是总参数量，而不是活跃的那部分。

KV 缓存 = 2 × 层数 × kv_heads × head_dim × 字节数 × 上下文 × 并发数。分组查询注意力 (kv_heads < attn_heads) 会大幅缩小这一数值——它从每个模型的配置中读取。多头潜在注意力 (DeepSeek) 则改为每个 token 缓存 层数 × (kv_lora_rank + qk_rope_head_dim) × 字节数。按 vLLM 的预留方式计算：滑动窗口层保留其窗口以及所有正在处理的 token（两个批次的 --max-num-batched-tokens），Mamba 或线性注意力层保留两个状态块。

开销 指 vLLM 0.31 在每个 GPU 上除权重和缓存之外保留的内容：运行时缓冲区（对它可能批处理的每个序列，词汇表中每个条目 4 字节）、性能分析运行的峰值（批处理 token 经过前馈层块与输出层二者中的较大值）以及 CUDA 图。使用张量并行时，每个 GPU 都保留自己的一份。经 vLLM 十一次启动对照验证，与 vLLM 自身的数值相差在 0.13 GiB 以内。每张显卡的预算按 vLLM 的 --gpu-memory-utilization 计算，默认为 0.92。

估算仅供规划参考，不作保证。实际用量因推理引擎 (vLLM, TGI, llama.cpp) 及其分页注意力效率而异。

这个计算器的假设

LLMScale 从 Hugging Face Hub 上每个模型的 config.json 读取其架构 — 层数、注意力头和键值头、head size — 并据此估算 GPU 显存，而不是只看参数量。Llama、Gemma 和 Mistral 等受控模型的配置无法由浏览器读取，数据来自内置数据库；没有自身配置的仓库（例如 GGUF 派生仓库）通过其 base_model 解析。

每个 GPU 都按 vLLM 的默认比例，即显存的 92% 计算预算；其余部分留给 CUDA 上下文。在权重和 KV 缓存之外，每个 GPU 还要承担 vLLM 自身的开销：运行时缓冲区、性能分析阶段的峰值以及 CUDA 图，这些都对照真实的 vLLM 启动过程测量过。统一内存设备不按整个内存池计算，而是用一个现实的比例：Apple Mac 内存的 75%（36 GB 以下的机型为三分之二）；在 Strix Halo 和 DGX Spark 上，取 GPU 报告值的 92%（vLLM 的比例）— Strix Halo 分给 GPU 的 96 GB 中的 88 GB，DGX Spark 121.6 GB 中的 112 GB（在 DGX Spark 上 vLLM 通常以 80% 运行）。每个 GPU 的预算都从其运行时报告的显存出发，这个值略低于标称容量；在开启 ECC 的 GDDR 数据中心显卡上（L40S、L4、T4）还要再少十六分之一。解码速度取显存带宽（按厂商峰值的 80% 计）与稠密算力两者所限中较慢的一个。首 token 延迟按单个请求、不排队时提示的 FLOPs 计算。算力在 GeForce 显卡上按额定峰值的 90% 计，依据是在 RTX 4070 Ti 上用 vLLM 的实测（测试卡的实际频率高于其额定数值所依据的频率）；在其他显卡上按 60% 计，属于估计。这些数字用于容量规划 — 推理引擎及其分页注意力效率仍会影响实际数值。

常见问题

70B 模型需要多少 VRAM？
以 Llama 3.3 70B 为例，仅权重在 BF16 下约需 131 GiB，FP8 下 68 GiB，INT4 下 38 GiB：706 亿个参数，每个 2 字节；之后 Transformer 层改为 1 字节或约 4.25 bit，而嵌入层和输出层像量化检查点那样保持 16 bit。KV 缓存和开销另外计算，两者都取决于上下文窗口和用户数 — 这正是计算器要算的。
为什么上下文窗口对结果影响这么大？
KV 缓存随上下文长度和并发用户数线性增长。Llama 3.1 8B 在 FP16 下每个 token 存储 131,072 字节：单用户 8k token 时为 1 GiB，128k 时为 16 GiB — 而 16 个用户各 8k token 时同样是 16 GiB。
混合专家模型需要的显存更少吗？
显存上并不会更少。每个专家都必须加载，所以显存按总参数量估算。每个 token 只运行部分专家，这就是 MoE 模型生成速度比其规模看起来更快的原因。
DeepSeek 的 KV 缓存怎么处理？
DeepSeek-V2 和 V3 使用多头潜在注意力 (MLA)，每层只缓存一个压缩后的潜在向量，而不是每个头的键和值。计算器从配置中读取 kv_lora_rank 和 qk_rope_head_dim，每个 token 按 层数 × (kv_lora_rank + qk_rope_head_dim) × 字节数 计算。DeepSeek-V3 在 8k 上下文下为 0.54 GiB，而通常的公式会得出 13.34 GiB。DeepSeek-V3.2 的稀疏注意力和 DeepSeek-V4 的压缩注意力也以同样方式根据各自的 config.json 估算。
