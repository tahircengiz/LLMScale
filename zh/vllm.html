如何选择 vllm serve 参数

选择模型、GPU 及其数量、上下文长度、优先目标（均衡、吞吐量、低延迟、最高准确度或显存紧张）和任务（聊天、RAG、代码、工具调用、结构化 JSON、视觉或推理）。助手会据此生成一条 vllm serve 命令，每个参数附一行理由，并提供同样参数的 Kubernetes args 形式。

  • --max-model-len = 你设置的上下文
  • --tensor-parallel-size、--pipeline-parallel-size、--data-parallel-size 和 --enable-expert-parallel = 计算器在这么多 GPU 上给出的布局：在 vLLM 能在这些 GPU 上运行该模型、且能在该上下文下容纳这些请求的方式中，取最快的一个（与它相差 10% 以内的方式中，取容纳请求最多的；若优先吞吐量或显存，则取容纳请求最多的），仅当没有其他布局装得下时才使用流水线阶段（或者使用链接或布局选择器指定的布局）
  • --gpu-memory-utilization = 优化吞吐量或显存紧张时为 0.95；否则保持 vLLM 的默认值 0.92 不变
  • --kv-cache-dtype fp8 = 优先显存紧张或吞吐量，且上下文为 32k+ 或任务为 RAG 时；DeepSeek V4 则始终使用，并配合 --block-size 256，与其 vLLM recipe 的设置一致
  • --max-num-seqs = 512（吞吐量）、32（低延迟）或 64（显存紧张），上限为每个 GPU 分摊权重和 vLLM 开销后，KV 缓存所能容纳的满长度序列数
  • vLLM 0.31 默认开启前缀缓存和分块预填充，因此命令中不包含它们

工具调用会加上 --enable-auto-tool-choice 以及该模型系列的工具调用解析器，结构化 JSON 会加上 xgrammar 后端，视觉任务会限制每个提示的图片数。预量化仓库（AWQ、GPTQ、FP8、NVFP4）不需要 --quantization 参数，页面也会注明。显存检查 — 即 VRAM 计算器自己对布局中每个 GPU 上一个满长度请求的估算 — 会在模型装不下时发出警告，并给出计算器算出的所需 GPU 数量和布局方式。Apple 设备不在其列，因为 vLLM 没有 Metal 后端。

常见问题

--gpu-memory-utilization 有什么作用？
它是 vLLM 可以从每个 GPU 显存中取用的比例，用于模型权重、激活值和 KV 缓存。权重用不完的部分会成为 KV 缓存，因此值越高，可容纳的并发序列越多，留给该 GPU 上其他程序的余量也越少。
为什么 --max-num-seqs 比我预期的低？
本工具会把它限制在你所选上下文长度下 KV 缓存实际能容纳的数量。设得更高并不会增加容量：超出这个数量的请求会在队列中等待。
我应该使用 FP8 KV 缓存吗？
它能把 KV 缓存减半，因此可容纳的序列数大约翻倍，但在长上下文任务中可能损失准确率。所以本工具只在优先考虑显存或吞吐量且上下文较长时才建议使用，并要求你先验证。
我需要多少个 GPU，它们如何划分？
足以放下权重和你的工作负载所需的 KV 缓存即可。当一个 GPU 放不下时，显存检查会给出显存计算器算出的数量和布局：注意力头能均分时用张量并行；不能均分，或缓存无法再拆分时，用流水线阶段；对于 MoE，则把专家分布到各个数据并行 rank 上。容量规划会针对给定负载为同样的布局确定规模。
