config.json 解读——用通俗的语言读懂 LLM 的配置

Hugging Face 上的每个模型都附带一个 config.json——几十个字段，决定了它的显存、速度以及能读多长的内容。选择一个模型，本页会用通俗的语言回答这些字段所决定的问题，并指出每个答案所依据的文件行。

如何读取配置

config.json 是 Hugging Face Transformers、vLLM 和其他引擎在加载权重之前用来构建模型的文件。它记录了架构——层、宽度、注意力头、专家、位置、词汇表和精度——但不包含权重，也不包含参数量；参数量由 LLMScale 从 Hugging Face API 获取。

  • 每 token 的 KV 缓存 = 2 × 层数 × 键值头数 × head_dim × 字节数
  • MLA 下 = 层数 × (kv_lora_rank + qk_rope_head_dim) × 字节数
  • 最大上下文 = max_position_embeddings（线性缩放和 YaRN 缩放按“原始长度 × 系数”达到该值；Llama 3 缩放无法这样相乘得出）
  • GQA 比例 = 注意力头数 ÷ 键值头数

每个答案都会列出它用到的字段并在文件中高亮显示，下方附有计算过程。术语表不认识的字段会连同原始值列为未解释，而不是去猜测。Llama 和 Gemma 等受控仓库无法从浏览器读取；对于这些仓库，本页会退而使用 LLMScale 内置数据库中的架构，并加以说明。

常见问题

config.json 里的参数量在哪里？
不在里面。配置描述的是模型的形状，而不是它在磁盘上的大小。LLMScale 从 Hugging Face API 上的 safetensors 元数据读取参数量，因此本页才能把它显示在配置旁边。
num_attention_heads 和 num_key_value_heads 有什么区别？
num_attention_heads 是每层运行的查询头数量；num_key_value_heads 是这些查询头共享的键头和值头数量。当后者更小时，模型使用的是分组查询注意力，其 KV 缓存也按相同比例缩小——Llama 3.1 8B 的 32 个查询头共享 8 个键值头，所需缓存是完整多头注意力的四分之一。
max_position_embeddings 是否意味着模型在该长度下表现良好？
它表示模型被配置为支持该长度。引擎以它为起点，但默认值可能更低——Ollama 会根据你的显存来设定，vLLM 则让 LongRoPE 模型默认使用其原始长度。模型在接近上限时表现如何取决于它的训练方式，而这是配置无法告诉你的。
为什么 trust_remote_code 很重要？
auto_map 条目表示该仓库附带自己的 Python 模型代码，而 Transformers 只有在你传入 trust_remote_code=True 时才会运行它。这些代码以你的权限运行，所以请先阅读——或者优先选择 Transformers 原生支持的模型版本。
