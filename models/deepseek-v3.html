DeepSeek V3: how much VRAM does it need?

DeepSeek V3 has 684.53B parameters in 61 layers. It uses multi-head latent attention (MLA): each layer caches one compressed 576-dimensional latent per token instead of keys and values for every head, which makes its KV cache 24.9× smaller than the usual formula would give. It is a Mixture-of-Experts model with about 37.00B of its 684.53B parameters active per token: memory has to hold all of them, while each token passes through only the active share. It takes up to 163,840 tokens of context; one user at that length needs 10.72 GiB of KV cache at FP16 on top of the weights.

One user, FP16 KV cache, 10% activation overhead and 0.75 GiB of CUDA context. Quantizing shrinks the weights, not the KV cache, so the saving narrows as the context grows.

Which single GPUs hold it

  • BF16 (1403.9 GiB): no single GPU holds it — by memory it takes 19× H100 (SXM/PCIe) 80GB, 11× H200 141GB, 8× B200 192GB.
  • FP8 (702.6 GiB): no single GPU holds it — by memory it takes 10× H100 (SXM/PCIe) 80GB, 6× H200 141GB, 4× B200 192GB.
  • INT4 (352.0 GiB): Apple M3 Ultra (512GB)

At 8k context for one user, the smallest cards first. A discrete card is budgeted at 95% of its memory; a unified-memory device at the share its GPU can address.

How many users fit

No single card here holds it at any precision; serving it means splitting it across several GPUs with tensor parallelism.

Where the numbers come from

Weights are parameters × bytes per parameter. With MLA the KV cache is layers × (kv_lora_rank + qk_rope_head_dim) × bytes × context × users. For DeepSeek V3 that is 68.6 KiB per token at FP16. These are capacity-planning figures: the serving engine — vLLM, TGI, llama.cpp — and its paged-attention efficiency still move the real number.
