How the vllm serve flags are chosen

Pick a model, a GPU and how many of them, a context length, a priority (balanced, throughput, low latency, max accuracy or memory-tight) and a task (chat, RAG, code, tool use, structured JSON, vision or reasoning). The helper turns that into a vllm serve command with a one-line reason for every flag, and the same flags as Kubernetes args.

  • --max-model-len = the context you set
  • --tensor-parallel-size = number of GPUs, plus --enable-expert-parallel for MoE models
  • --gpu-memory-utilization = 0.95 for throughput or memory-tight, 0.90 otherwise
  • --kv-cache-dtype fp8 = memory-tight or throughput priority, with 32k+ context or a RAG task
  • --max-num-seqs = 512 (throughput), 32 (low latency) or 64 (memory-tight), capped at ⌊((GPUs × VRAM × utilization − 1 GiB) ÷ 1.1 − weights) ÷ KV per sequence⌋
  • --enable-prefix-caching for chat, RAG, tool use and reasoning; --enable-chunked-prefill for long context

Tool use adds --enable-auto-tool-choice with the tool-call parser for the model's family, structured JSON adds the xgrammar backend, and vision limits images per prompt. Pre-quantized repositories (AWQ, GPTQ, FP8, NVFP4) need no --quantization flag, and the page says so. A memory check — weights plus one full-length sequence of KV cache, × 1.1, + 1 GiB — warns when the model will not fit; it is coarser than the VRAM calculator, so use that for exact sizing. Apple devices are left out because vLLM has no Metal backend.

Questions

What does --gpu-memory-utilization do?
It is the fraction of each GPU's memory vLLM may take for model weights, activations and KV cache. What the weights do not use becomes KV cache, so a higher value fits more concurrent sequences and leaves less headroom for anything else on the card.
Why is --max-num-seqs lower than I expected?
The helper caps it at what the KV cache can actually hold at the context length you chose. Setting it higher does not add capacity: requests past that point wait in the queue.
Should I use an FP8 KV cache?
It halves the KV cache, so roughly twice as many sequences fit, but it can cost accuracy on long-context work. That is why the helper only suggests it when memory or throughput is the priority and the context is long, and asks you to validate it first.
How many GPUs do I need for tensor parallelism?
Enough for the weights and your workload's KV cache to fit. The memory check here estimates how many; the VRAM calculator shows the exact figure per card and suggests a GPU count that splits the model's key-value heads evenly.
