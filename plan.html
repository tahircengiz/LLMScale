A planning model for steady traffic at average lengths, without spikes. Reading prompts takes a share of each replica's time and stretches decode by the same factor; the number of sequences in decode follows Little's law. Speeds are constrained by memory bandwidth at 80% of the vendor's peak and dense tensor throughput at 90% on GeForce cards (measured) or 60% on other cards (estimated). Memory usage comes from vLLM's own accounting. Leave headroom for bursts. Speeds are upper bounds until they are calibrated on more cards; across several GPUs they also leave out the communication between them, so multi-GPU figures are optimistic.

How the plan is worked out

One replica is a vLLM instance on one GPU or on a tensor-parallel group. At a given request rate, it spends part of its time reading prompts. The prompt time is the prompt's FLOPs divided by the attainable dense tensor throughput of the GPU (90% of the peak on GeForce cards, measured; 60% on other cards, estimated), or the time required to read the weights once if that is longer. The rest of its time goes to decode steps, so prompt and decode times stretch by the same factor. The step time at a given batch size comes from the decode model: the longer of the time required to read the weights and KV cache and the time required for the matrix multiplications. The planner finds the highest rate that keeps the time to first token, the time per output token and the KV cache within bounds, and divides the load by it.

  • prefill share f = requests per second per replica × prefill time
  • time per output token = decode step at the batch ÷ (1 − f)
  • sequences in decode = requests per second × output tokens × time per output token
  • GPUs = ⌈requests per second ÷ one replica's capacity⌉ × tensor-parallel size

It tries every tensor-parallel size up to 8 that the model fits and vLLM can split its heads across, and lists them cheapest first. A shared prefix is cached once and not recomputed. Arrivals are assumed to be steady, and prompt and output lengths are represented by their averages, so real traffic with bursts and long tails needs additional headroom.

Questions

Why can a model that fits one GPU need several?
Memory says whether a model runs; the load says how many copies it takes. Every request first has its prompt read, which is compute-bound, and then holds a slot in every decode step until its reply ends. Llama 3.1 8B fits one H100 with room to spare, yet at 2,048-token prompts and 256-token replies with a 50 ms per-token target one H100 carries about 10 requests a second, so 15 a second take two.
Why does tensor parallelism sometimes cost no more GPUs?
Splitting a model across GPUs splits the weights each step reads and the work each prompt needs, so each step is shorter and each prompt is read sooner. When a latency target is what limits a replica, two GPUs as one replica can carry more than twice what one does; when the KV cache or raw throughput limits it, separate replicas are as good and simpler.
How far can I trust the figures?
They are first-order. Memory comes from vLLM's own accounting, checked against real startups. The speeds use vendor peaks with stated efficiencies, and the queueing model assumes steady arrivals. Treat the GPU count as the floor for your average load and add 20 to 30% for bursts, then confirm with a benchmark on one replica.
