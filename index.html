How the numbers are calculated ▸▾

Weights = parameters × bytes/param (FP16/BF16 = 2, FP8/INT8 = 1, INT4 = 0.5). For Mixture-of-Experts models, all experts are loaded, so total params are used — not the active subset.

KV cache = 2 × layers × kv_heads × head_dim × bytes × context × concurrency. Grouped-Query Attention (kv_heads < attn_heads) shrinks this dramatically — it's read from each model's config. Multi-head latent attention (DeepSeek) caches layers × (kv_lora_rank + qk_rope_head_dim) × bytes per token instead.

Overhead adds activations + fragmentation (a configurable %) plus a fixed CUDA context allowance. GPU fit assumes ~95% of nominal VRAM is usable.

Estimates are for planning, not a guarantee. Real usage varies by serving engine (vLLM, TGI, llama.cpp) and its paged-attention efficiency.

What this calculator assumes

LLMScale reads each model's architecture from its config.json on the Hugging Face Hub — layers, attention and key-value heads, head size — and sizes GPU memory from that, not from the parameter count alone. Gated models such as Llama, Gemma and Mistral, whose config a browser cannot read, come from a bundled database; a repository without a config of its own, such as a GGUF fork, is resolved through its base_model.

Every card is budgeted at 95% of its nominal memory. Unified-memory devices use a realistic share instead of the whole pool: 75% of an Apple Mac's memory, 96 of 128 GB on Strix Halo, 120 of 128 GB on DGX Spark. Decode speed is estimated from memory bandwidth at 80% efficiency; prompt processing (prefill) is not modelled. The figures are for capacity planning — the serving engine and its paged-attention efficiency still move the real number.

Questions

How much VRAM does a 70B model need?
The weights alone take about 130 GiB at BF16, 65 GiB at FP8 and 33 GiB at INT4 (70 billion parameters × 2, 1 or 0.5 bytes). The KV cache and overhead come on top, and both depend on the context window and the number of users — which is what the calculator works out.
Why does the context window change the answer so much?
The KV cache grows linearly with context length and with concurrent users. Llama 3.1 8B stores 131,072 bytes per token at FP16: 1 GiB for one user at 8k tokens, 16 GiB at 128k — and 16 GiB again at 8k with 16 users.
Does a Mixture-of-Experts model need less memory?
Not for memory. Every expert has to be loaded, so memory is sized from the total parameter count. Only some of the experts run for each token, which is why MoE models generate faster than their size suggests.
How is DeepSeek's KV cache handled?
DeepSeek-V2 and V3 use multi-head latent attention (MLA), which caches one compressed latent per layer instead of keys and values for every head. The calculator reads kv_lora_rank and qk_rope_head_dim from the config and uses layers × (kv_lora_rank + qk_rope_head_dim) × bytes per token. For DeepSeek-V3 at 8k context that is 0.54 GiB, where the usual formula would give 13.34 GiB.
